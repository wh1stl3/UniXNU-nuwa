All addresses below are decoded from the new final image using existing
Capstone5.0.7, with unchanged relevant native/module bytes proved by the stage
diffs. This is static dataflow, not a run or a hardware-monitor claim:

1. Native `_code_signing_configuration = 0xfffffff00771fd60` writes zero to
   `_cs_monitor = 0xfffffff00719fafc` using `STR WZR` at `...771fea8`, then
   loads that global and writes `monitor_type_out` at `...771fed0` (first
   argument retained in x20). Initial cs_monitor bytes are also zero.
2. AppleImage4 call `...46f13f0` → import stub `...46f9e78` → that exact native
   symbol passes x0=`0xfffffff005cb14b8`, x1=0. Thus this output slot receives
   software monitor=0, not a value guessed from monitor-exports NULL.
3. PMAP's first helper `...46f0e80` returns config base
   `0xfffffff005cb1310`. At `...46e9920`, LDRB reads base+0x1a8 = the **same
   output slot**; `...46e9924` tests bit1. Under this provider's normal zero
   result that branch is not taken. The original branch target
   `...46e9a44` and its canary/SP400 restores/tail-log **BR x4** at
   `...46e9aa0` remain intact; this is not another truncated return path.
   This excludes that specific monitor-bit1 tail route under the established
   software-provider condition, not all faults or alternate control flows.
4. The mode==2 `_kernel_image4_get_monitor_exports` path returning NULL is a
   **different**, conditional pointer-source path; it is not item1's cause.
5. PMAP runtime +0x58 is its `i4rt_context`, the Darwin runtime. It is not
   physical CPU secondary opt-in. Real ArmCpu `probe` initializes `[SP,#12]`
   with WZR at `...798f1d8`, then parses `sheng-smp` at `...798f1ec` (4-byte
   output). Source `ArmCpu.cpp:220–225` confirms default0/opt-in requirement.
   Current board payload args are `-v serial=3 sheng-platform-stage=5`, no
   sheng-smp; this is config evidence, not observation of an actual boot or
   a promise that future CLI args cannot override it.
6. Actual runtime dispatcher call `...46f141c` precedes public-interface
   registration `...46f183c` (version18 table); that order was independently
   established for the frozen layout and the critical calls are decoded again.
   PMAP's normal-RET truncation therefore does not prove downstream public
