# nuwa ADT 生成器落地与板级值溯源

2026-10-24。本轮只做离线生成与静态审计，无手机、USB 介质或固件行为改动。

## 结论

设备仓此前缺 `make-nuwa-adt.py`：基座契约要求设备仓提供该工具（`docs/zh/porting/device-tree.md:200`），而 `board.toml` 的 `[payload.adt] tool` 一直是 TODO。没有 `kernel.macho.adt`，`ArmDTPlatform::configure()` 必然失败，OS 入口的 blocker 3（"真实 nuwa Apple ADT 与运行时分配窗口未提供"）无法推进。

本轮补齐三个脚本并完成结构验证：

| 文件 | 职责 |
| --- | --- |
| `scripts/make-nuwa-adt.py` | 按基座契约生成 `kernel.macho.adt` |
| `scripts/check-nuwa-adt.py` | 独立有界解码 + 结构不变量审计（不复用生成器的编码器） |
| `scripts/audit-nuwa-adt-inputs.py` | 把生成器每个常量对回实机 FDT |
| `scripts/test-nuwa-adt.py` | 端到端正负例：真生成器的产物必须过，故意违约的树必须被拒 |

结果：最小树 12 节点 / 20 项检查 / 0 失败；完整参数树 21 节点 / 35 项检查 / 0 失败；板级常量 14 项对照中 10 项精确相等、0 项不符；正负例 8 个用例全部符合预期（3 个正面生成、4 个违约树、1 个生成器参数拒绝）。**这不代表内核能启动，也不代表固件能满足窗口请求。**

## 契约（对齐基座 payload 步骤）

`scripts/unixnu/payload.py:149-170` 决定参数集合，比旧路线版本多三个参数，旧实现会直接因未知参数失败：

- `--gpu-addon`：`/chosen/memory-map/GpuAddon` 16 字节占位符（`DarwinBoot.c:235`）。
- `--text-fixup`：`/chosen/text-fixups`，NUL 分隔表；消费方是 `patches/xnu/native-text-fixup.patch:110`，不进 1000 字节命令行。
- `--persistent-data`：Data 种子非临时，省略 `/chosen/ephemeral-storage`。

另外旧实现把 `--unique-chip-id` 与 `--chip-id` 强制成对校验，而 `payload.py` 是分别按 `[payload.adt]` 与命令行/环境变量独立传入的（`:150-155`），保留成对校验以免生成半个身份。

## 板级值溯源

全部来自 `out/live-nuwa-dt/android-dt-after-r011/android-live.dtb`（实机活动 FDT，4815 节点）：

| 常量 | 值 | FDT 证据 |
| --- | --- | --- |
| `TIMEBASE` | 19200000 | `/soc/timer` `clock-frequency = <0x124f800>` |
| `GIC_DIST` / size | `0x17100000` / `0x10000` | `/soc/interrupt-controller@17100000` reg[0..1] |
| `GIC_REDIST` / size | `0x17180000` / `0x200000` | 同节点 reg[2..3] |
| `GIC_REDIST_STRIDE` | `0x40000` | 同节点 `redistributor-stride` |
| `PSCI_METHOD` | `smc` | `/soc/psci` `method` |
| `CPU_AFFINITY1` | `0x0..0x700` | 8 个 `/cpus/cpu@N` |
| `UFS_HC` / size | `0x1d84000` / `0x3000` | `/soc/ufshc@1d84000` reg[0..1] |
| `DRAM_BASE` | `0x8c0000000` | `/memory` 合并连续段的最大段起点 |

`/memory` 的 9 个 reg 条目合并成 8 段连续区，最大一段跨度 `0x240000000`，与 D-001 的 9216 MiB 主 bank 独立吻合。

## 两处证据分歧及判断

**1. 根 `compatible`。** 旧路线实现写 `xiaomi,nuwa` / `qcom,sm8550`，注释称来自编译期 board DT；实机运行 FDT 报的是 `qcom,kalama-mtp` / `qcom,kalama` / `qcom,mtp`，`model` 为 `Qualcomm Technologies, Inc. 8550 nuwa`。

判断（置信高）：`ArmDTPlatform::configure()` 只检查 `/cpus`、`/arm-io`、`/defaults`、`/options` 与可用 CHRP NVRAM proxy（`drivers/ArmDTPlatform/ArmDTPlatform.cpp:123-142`），**不匹配根 `compatible`**；驱动匹配发生在 arm-io 子节点上（`NativeUfs.cpp:128` 找 `qcom,sm8550-ufshc`）。因此该属性在本路径下是硬件标签而非选择键，采用实机值更可追溯。反对证据：若后续出现按 compatible 匹配的平台专家，此值会变成选择键。最小证伪：内核跑起来后读 IORegistry 平台节点或看 `IOLog` 是否有平台专家未匹配。

**2. DRAM 末尾一页。** iomem 的 System RAM 跨度为 `0x23FFFF000`，FDT 的 `/memory` 跨度为 `0x240000000`，**差 `0x1000`（最后一页）**，不是此前近似表述暗示的差 55 MiB。判断：`dram-size` 是广告值不是分配承诺，取 FDT 的 `0x240000000` 与 D-001 一致且满足 2 MiB 对齐；窗口实际可用性交给 `owned-memory-size` 与 UEFI 内存图验证。取值本身受 AGENTS §3.1 约束，已写入 `docs/NEED-REVIEW.md` R-012 待批。

## R-012 获批：board 写入两个受审字段并复核组装

用户 2026-10-24 18:40 回复「批准A继续推进」，按最小范围只写两个字段：`[payload] dram_size = "0x240000000"`、`[payload.adt] owned_memory_size = "0x40000000"`。`example = true`、其余 TODO、所有 `_verified` 均未动，无设备动作。

新增 `scripts/check-nuwa-adt-board.py`：因为 `config.py:103` 会拒绝 `example = true` 的 board，基座 payload 步骤本身跑不起来，所以该脚本按 `payload.py:149-170` 的规则从 board.toml 组装同一条命令行，离线驱动生成器并交给独立检查器。两种场景都通过：

| 场景 | 节点 | 结构检查 | 失败 |
| --- | --- | --- | --- |
| board 仅 ADT 配置 | 21 | 31 | 0 |
| board + ramdisk/trustcache/gpuaddon | 21 | 34 | 0 |

**复核中发现一处真实的契约不兼容**：旧实现（含我第一版）强制 `--unique-chip-id` 与 `--chip-id` 成对出现，但基座是分别传的 —— `--chip-id` 来自 `[payload.adt]`，`--unique-chip-id` 来自命令行或 `UNIXNU_UNIQUE_CHIP_ID`（`payload.py:150-155`）。board 的 `chip_id` 目前是 TODO，只给 seed 时生成器会直接 exit 2，把整条 payload 步骤卡死。已改为允许独立传入、只告警，且各自独立写入 `/chosen`；两者同时存在才可能生成 `IOPlatformUUID`。`scripts/test-nuwa-adt.py` 增加了 `seed-without-chip-id` 用例锁住这个行为。

这条正好说明为什么"照抄旧实现"不够：旧实现活在 P16 路线里，没被当前的基座传参路径验证过。


## 产物与复现

```bash
# 生成（最小：无 sidecar）
python3 scripts/make-nuwa-adt.py --output out/adt-nuwa/min.adt --dram-size 0x240000000
# 结构审计
python3 scripts/check-nuwa-adt.py --adt out/adt-nuwa/min.adt --output reports/<新路径>/min.json
# 常量溯源
python3 scripts/audit-nuwa-adt-inputs.py --fdt out/live-nuwa-dt/android-dt-after-r011/android-live.dtb \
    --output reports/<新路径>/inputs.json
# 正负例
python3 scripts/test-nuwa-adt.py --output reports/<新路径>/test.json
# 按 board.toml 复核 payload 参数组装
python3 scripts/check-nuwa-adt-board.py --seed <hex> --sidecars --output reports/<新路径>/board.json
```

本轮证据：`reports/adt-nuwa/2026-10-24/{min,board,board-with-sidecars,inputs,test}.json`。`board-with-sidecars` 覆盖 ipad 身份、8 核、RAMDisk/TrustCache/GpuAddon 占位符、1 GiB owned 窗口、平台种子。

负面用例的意义在于反向证明：缺 `/options` 被拒（`ArmDTPlatform::configure()` 的必需节点）、`RAMDisk` 与 `PackedRAMDisk` 并存被拒（`DarwinBoot.c:224-227` 的 KeepPacked 逻辑）、owned 窗口低于 256 MiB 或越过广告 DRAM 被拒。只验证"合法输入能过"的检查器无法排除"永远通过"。

## 未验证边界

- 固件能否满足 `owned-memory-size` 请求的连续区：**未验证**，需 UEFI 内存图与实际分配。
- XNU 是否接受这棵树：**未验证**，无内核执行。
- 任何驱动是否在这些节点上绑定：**未验证**。
- 基座 payload 步骤本身是否接受该 board：**未验证**，`config.py:103` 仍以 `example = true` 拒绝；本轮的复核是离线重放参数组装，不等于跑了基座。
- `[payload] dram_size` 与 `owned_memory_size` 已按 R-012 A 写入，但它们的**正确性**只到"与实机 FDT 和 D-001/D-002 一致"，窗口可用性仍未证。
